# Product discovery for agents who cannot infer a brief
Check if the user has given you a local project, source, URL, HTML, notes, screenshots or product assets. If enough, begin. If not, ask in one message: “Send any ONE of: the project/source ZIP, website URL, saved HTML (if the URL cannot be fetched), or a short description of what the product does and what makes it different. For the full video also send your song file, unless you want to waive music.” The user decides. Do not require all choices.

Local project: inspect filenames, README, routes, screenshots, design tokens, pricing and product copy; limit reading to relevant files; redact secrets, credentials and personal data. Never run arbitrary install/build commands without checking provenance. A source-code presence proves implementation exists, not live availability. For a URL use available browser/network or ask for HTML if unavailable; no bypassing restrictions. Static HTML cannot prove client-side behavior. Direct user description is evidence attributed to user, not independent verification. UI screenshots can prove appearance, not underlying security. For product footage capture authorized pages at the actual viewport, avoid PII and real account tokens. A mock must be visibly accurate and labeled in the delivery notes, no fabricated product functions.

Record `claim-id`, claim, source path/URL/user statement, status (live observed, implemented not confirmed live, user stated, planned, unverified), safe wording. Record assets with origin, license/permission and path. Use only confirmed claims in advertising; label future features explicitly and only if user wants teasers. Avoid fake scarcity/stats, competitor allegations, fake testimonials.

Decide audience, pain/aspiration, action, one key benefit, one proof moment. If target is not specified use a reasonable explicit assumption. Ask only if the missing information changes the video materially. Keep all other differentiators in campaign ledger. Do not ask for existing information again.
