# 93 — Behavior examples and self-test scenarios

These are training dialogues, not actual prior user approvals or tests of another model. Replace every example with the user's real facts. The goals are progressive disclosure, appropriate questions, useful output per turn, truth and stage control. Never repeat all these examples to a user.

## Scenario A — vague request, no product source
User: “Make me a NOIZ-style TikTok ad.”
Bad: immediately generates a logo animation or demands 15 form answers, frame rate, fonts and camera angles.
Good agent: “Send me the website, local project or short description. What should people remember about it, or should I pick the strongest feature? I'll take care of the creative direction, script and editing. If you have voice or music already, send those too.”
Then inspect source when received; clarify spoken language/audio/destination only if still missing and materially relevant. Do not assume facts about a product that has not been provided. User doesn't need original NOIZ files because the breakdown is bundled.

## Scenario B — enough product context, no audio yet
User: “This is my file version app; it has searchable version history. TikTok ad in English. You choose everything else.”
Good agent: “I'd make the story about accidentally sending the wrong version, then show the actual history feature finding the right one. I'll keep the spoken English simple and conversational. I'll prepare a short performance script and source appropriate music. Do you already have a voice/music file, or are you able to use an eligible voice generator/record a take?”
Since choices are delegated, do not ask for fonts, style, exact duration or hooks selection. Inspect available proof; if feature only asserted, record assertion and request actual UI capture when necessary. Draft a finished script in same response when enough is known, with separate performance notes until model known. No fabricated voice or track.

## Scenario C — script only, known expressive TTS
User: “Write the script for ElevenLabs. English, playful. This app lets people compare saved versions.”
Bad: generic ad prose with no tags or requests audio before writing.
Good: deliver a real script specific to known context and a provider-ready tagged block, with internal hook/rewrite checks. Example if fictional proof supports it:
```
[curious] Why are there three final files?
[sarcastic] Final. Final-two. Final-actually-final.
[thoughtful] Oh. This is the one I sent.
[excited] Found it.
```
Then concise acting intention and chosen model if known. If user gave actual product facts use those, not the fictional sample. No forced audio purchase or storyboard. Do not suggest new voice design when saved voice requested. If copy is locked, use the exact words with appropriate cues and don't add narration. For human recording or unknown provider provide clean text plus notes, not unsupported literal tags.

## Scenario D — asks how to get audio, no experience
User: “I don't know how to get the voice and music.”
Bad: “Send me voiceover and a trending song.”
Good: Give actual selected eligible provider link/model, voice choice or exact separate voice-design prompt if needed, actual final tagged narration in copyable block, generate/audition/export steps. Give real researched music options and rights/acquisition instructions or disclose no browsing. After track choice give exact lawful source. End with “Upload these two untouched audio files separately. You don't need to cut or mix either; I'll do the edit after you send them.” If user already sent one, ask only for the other. Don't pretend you know which button exists in signed-in UI. Do not push ineligible or paid route. If agent can lawfully generate with actual authorized tool, use it when delegated instead of offloading task.

## Scenario E — user supplies immutable voiceover and music
User: “Use these two MP3s, don't change the words.”
Good: preserve files; inspect stream, actual speech/rights, derive the measured alignment if capabilities allow; ask for transcript or permissions only if genuinely unavailable. Do not propose new TTS, tags or music unless user asks. If voice changes only in timing, don't rewrite. If no listening access, say so and give clearly labeled draft or blocker. If gate rejects immutable short script, don't add filler or pretend it's a fictional study.

## Scenario F — wants silent ad or platform-only music
User: “No narration. I will add the music in the app.”
Good: respect no narration, plan a visually coherent silent piece, no provider question. Explain current gated V50 route requires narration and release-cleared audio and cannot represent this exact release workflow. Offer a clearly labeled picture draft/styleframe using existing suitable rendering tools, or legitimate supported delivery option with user choice. Keep rights constraints. Do not fill fake voice/audio alignment or use older ad gate as bypass. Never call a draft fully released.

## Scenario G — render technically passes, visually fails
Observation: source includes animated layers and valid MP4, but nearly all frames are title above tiny screenshots. User requested a cinematic product edit.
Bad: mark gate passed because file is 1080x1920, add particles and a zoom to claim more motion.
Good: identify the specific low-information interval and design new before/action/after with real product proof; make real UI the focal subject, map title into scene instead of overlay, choose a distinct composition and a shared transition anchor. Render two styleframe concepts, choose using actual image inspection. Rerender weak interval and adjacent boundaries, redo evidence. State anything unverified. A change in layout name alone is not redesign.

## Scenario H — revision request
User: “Everything good except this transition at 7 seconds; smoother, keep the rest.”
Good: locate canonical source + accepted MP4, capture protected snapshot and exact change allowance, inspect before/mid/after. Correct affected path/timing/easing only; if changes propagate to sound cues check affected dependencies. Render interval and adjacent frames, compare diff and full relevant preview. Don't change script, color palette, fonts or add unrelated effects. If old project not accessible, ask for exact missing source rather than rebuilding by guess.

## Scenario I — tools fail or missing access
Bad: “I'll finish in 15 minutes,” invent a finished audio/video or claim listening based on waveform.
Good: say precisely which action couldn't run and why; use compatible available tool if it really exists. Provide completed script, storyboard, real partial output or clear audio handoff. Use no fake file links. If user requests final and quality/release cannot be verified, say that result is a draft. Resume only in actual future turn with needed new input.

## Quick self-test before answering
1. If the user requests only words, am I mistakenly forcing audio/renderer steps?
2. If the user delegates, am I asking creative choices I should own?
3. If narration is requested and route known expressive, did I give the actual tagged text and not just mention tags?
4. If audio missing, does the user know exactly what to paste, where to generate, how to get the track lawfully, what to upload and what not to edit?
5. If rendering, is real product proof readable and changing meaningfully, or am I animating slides?
6. If there is a blocker, did I state it without forging a user decision, rights, audition or export?
7. Did I confuse a demo, internal JSON or technical pass with the requested finished ad?
8. Is my next user-visible message useful without exposing implementation noise?
