# Data proof and coherent technical motion system

Use guide 26 as a reference study, not a template. Technical stories are useful when a product has a genuine interaction or measured data. Do not fake monitoring, performance, account counts, financial results, or security proof. If numbers are missing, show a real interaction, three illustrative steps or a conceptual diagram visibly labeled illustrative; avoid inventing "millions" or social proof. Each numeric claim needs source, period, unit, display precision, and whether the source is directly measured, user-provided, or illustrative. A successful mock UI is not evidence that production software works.

## Agent SOP
1. Define the actual problem, consequence, evidence, result, and desired action. Choose 1 main claim and up to 2 supporting claims. Write the final provider-specific voice script first; no animation until audio is received/waived. Prepare source material read-only; remove usernames, secrets, private logs and unrelated URLs.
2. Choose a data model appropriate to the story: ordered time series for trend, categories for bar chart, records for a log, actual relationships for a network. Sort chronological records, define units, ensure axis starts at zero when claiming bar size comparisons; if axis truncation is necessary label it clearly. Do not use decorative random wiggles as measured charts. Keep metadata in production files; visible concise label on meaningful data.
3. Use a layout map with one focal point, left text edge, fixed plot baseline and clear empty space. Build an animated data graphic with actual values linked to a counter. A chart should remain readable after pausing at any progress point. Avoid expensive HTML layout reflow; use SVG viewBox, absolute coordinates, transforms, clipping, fixed tabular figures. Preview at target phone size.
4. Use representation changes as narrative beats: single record -> several -> chart -> one number -> reset. Plan a constant header and preserve the focus anchor. On-screen headline should add or emphasize information, not duplicate all VO as oversized captions. Use real captions separately. Every 0.5–3s is a *candidate* beat boundary depending on audio; don't force cuts when it damages comprehension.
5. In a rapid proof montage, prioritize comprehension over number of claims. Show one distinct state at a time. If a title or graphic cannot be read at normal playback, simplify/remove it or give more time. Use a slower hold immediately after intense density, and a product proof shot before CTA. Prefer purposeful cuts to identical zoom transitions.
6. Use starter/data_motion.py as a smoke-tested primitive for three technical motion modes; it renders at fixed fps from a single explicit series. It is a learning/demo clip with illustrative facts, NOT an ad renderer or substitute for project-specific design. It requires Pillow and ffmpeg. Run with the example config; inspect frames and adapt geometry, timing and style. For production add actual VO and soundtrack with the established audio-first pipeline and required quality checks.
7. Before output, compare chart endpoint/counter and bars against actual source data; verify frame coverage, safe areas, contrast, readable labels, provenance and any conceptual labels; audit at least one frame per scene and boundaries. If numerical QA fails, fix data at its source rather than hiding label. If assets are missing, use nonnumeric truthful evidence or request one missing fact only when essential. Never use reference metrics as product claims.

## Minimum claim record example (illustrative only)
`{"claim_id":"sample","label":"Example series","unit":"items","period":"Demo steps 1–6","source":"Synthetic demo","illustrative":true,"values":[2,3,4,8,9,15]}`. Replace with real data as applicable. Keep illustrative labels on screen. No generated dataset may be marketed as measured facts. Avoid visual exaggeration.
