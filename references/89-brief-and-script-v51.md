# 89 — User intake and human copywriting

## Intake: decide what information is necessary
Inspect first. For a supplied URL, local app, files or HTML, inspect the real product without modifying or deploying it. For screenshots/description, use what is actually visible or stated. A screenshot cannot establish all behavior. Separate visible fact, user assertion, plausible inference and unknown; keep an evidence note for each central claim. Don't promise that external sources were examined if inaccessible. Request one alternative source when required, not all formats.

| Decision | Ask when | Don't ask when |
|---|---|---|
| Product / proof | Missing, inaccessible, or unverified factual claim is central | User gave usable URL/description/project and you can inspect it |
| Story focus | Several substantially different claims, no delegation | User specifies a feature or says pick one |
| Audience / action | Ambiguity changes language, CTA, story | Obvious from supplied brief or explicitly delegated |
| Spoken language | Not specified and not confidently inferable | Known from user instructions or approved text |
| Destination / use | License, format/overlay or CTA depends on it | Already known; public advertising defaults to commercial, not free personal use |
| Voice route | New narrated ad, no stem or route chosen | Existing audio, script-only, no-voice request, known provider |
| Music | Sound choice unknown and relevant | Existing music, no-music request, known delegated choice |
| Duration, tone | Hard constraints or genuine preference conflicts | Routine creative decision: recommend an appropriate length and tone |

No asking about fonts, frame rates, easing, transition recipes, GPU, how many 3D shots, or whether to create a storyboard unless user specifically cares. Recommend art direction yourself. Do not ask users to supply credentials, paid assets without consent, or every reference video. If only a script is requested, skip questions about export/audio unless relevant to the copy.

### Sample first responses (adapt, don't copy blindly)
**No source:** “Send me the website, project or a short description. What's the main thing you want viewers to remember, or should I pick it? If this is for TikTok/Shorts, I can plan the rest including script, voice and music.”
**Source available, unclear preferences:** “I can see [specific verified feature] and [actual relevant detail]. I'd make the video about [one outcome], not the whole app. Is it for [likely destination], and should the voice be English or German? Do you already have voice/music files, or should I prepare the voice script and suggest tracks?”
**Delegated:** “I'll focus on [verified outcome] for [audience], with a [reasoned tone] and a short [format]. I'll write the voiceover and choose the visual treatment; the only missing piece is [genuinely missing dependency].”
Do not output brackets to the user or claim you saw a feature when you didn't. These are templates for the *conversation*, not generic ad copy.

## Write the ad in five editorial passes
1. **Story premise**: one sentence in ordinary language: viewer does X, encounters Y, learns/achieves Z. Identify visible proof before asserting Z. One central idea, not a product tour. Label alternative features for future episodes instead of stuffing them into this one.
2. **Hook lab**: internally explore at least three genuinely different mechanisms: a recognizable situation, a surprising contradiction, a visual action/demo, a comedic reversal or a useful discovery. Three rephrasings of the same question do not count. Score qualitatively on specificity, immediate visual potential, truthful payoff, audience fit. Pick one (unless client wants to choose). Do not dump brainstorming if user asked for a final script. The opening line may be a statement, fragment or action; don't force “Bro,” “wait,” or a question each time.
3. **Clean draft**: opening tension → change/realization → actual result → natural ending. Use specific nouns, short clauses, varied rhythm, contractions where natural. Write for someone hearing it once, not reading a landing page. Keep phrasing simple without talking down. No repeated 'and...', feature inventories, fake competitor claims, vague “this changes everything”, filler, or CTA that promises something not proven. One sentence may span several shots, and a pause may carry the payoff. A brand can be named naturally; don't start with a logo unless story benefits. Rough length estimate depends on pace; 40–70 words/20–30 sec is a starting estimate, not a requirement; actual audio determines duration. Do not invent numerical proof or social metrics.
4. **Rewrite for the ear**: speak or audition when possible; if unable, perform honest text-based breath/punctuation review (not a claimed audition). Remove sentences that work unchanged for any app. Identify the exact emphasized word and emotional reason for each phrase. Use contrast between phrasing lengths. The selected opening must match the first `beats[0].text` exactly in the existing validator. If rewriting the hook, update candidate and locked text before handoff.
5. **Performance and lock**: use guide 90. Deliver clean narration for captions, provider-ready tagged text for TTS, and short separate direction; record confirmed or delegated decision. Do not send user a template with placeholders to fill. No random stage directions spoken. Do not change approved narration without permission. Text-only approval is not approval of the actual generated take.

## Specific rejection tests
- **Name swap:** would the entire script work for a different SaaS just by swapping name? Rewrite the affected lines.
- **Proof:** can the shown product or factual source demonstrate the claim? If no, cut or qualify it. A marketing screenshot is not evidence of safety or superiority.
- **Hook-to-payoff:** does the ending resolve what the first line made interesting? If no, rewrite the ending or hook, not add a feature.
- **Voice:** does this sound like a person rather than a press release? Try a shorter clause, a pause, or a concrete verb.
- **Visual:** each phrase has a potential subject/action; if all phrases only suggest text cards, choose a better story.
- **Audience:** slang is optional, not a substitute for specificity. Do not insult the viewer or competitors to get attention.

### Worked copy contrast based on the failed ad's topic (not verified product claims)
Weak: “You're about to run this script. You haven't read a single line of it. Most script sites just hand you a copy button. RobloxLarp shows you the source first. Read the code. See what it does. Keyless filters. Verified creators. Real views and copies.” (Visible captions from the submitted sample, not verified speech.) It starts with a generic admonition and ends with disconnected features/claims. Stronger *conditional* direction, if actual inspectable source UI is verified: “That copy button is tempting. But what are you actually copying? Open the source first. Read the part you're curious about. Then decide.” The demo must show real source access; not claim reading guarantees safety or endorse unknown code execution. In a real campaign refine copy after proof and audience; this is a teaching example, not ready-made branding or approved narration.

### Fictional worked script (file-version app; illustrative only)
Premise: a person is lost among versions, then visibly identifies the chosen file using the verified version feature. Distinct hooks: “Why are there three final files?” (confusion), “I think I sent the wrong version.” (confession), “Watch what happens to this folder.” (demo). Only select after actual product proof. If fictional storyboard assumes version history, label it fictional, never use as proof for a real product.
Selected clean example: “Why are there three final files? / Final. Final-two. Final-actually-final. / Oh. This is the one I sent. / Found it.” Play the first line curious, list dry, discovery softer, end with a small relieved smile. No arbitrary numeric or safety promises. This demonstrates rhythm, not universal scripting.

## User response expectations
If user chose expressive TTS, the actual tagged block is mandatory even if the client first asks for a script brainstorm to be refined into final copy. If provider is unknown, give the script and separate performance notes; offer the most appropriate supported route and explain that exact tags depend on model. Never silently output a plain script for a known expressive route. Ask for approval only if the client has not delegated and a meaningful selection is unresolved. Script-only deliverables are not blocked by tool gate heuristics.
